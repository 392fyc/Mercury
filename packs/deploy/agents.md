## Mercury updates (deploy pack)

- `.github/workflows/mercury-update.yml` and `.github/workflows/mercury-verify.yml` are managed files: Mercury renders them from `params` in `.mercury/config.json` (`integration_branch`, `required_checks`, `update_schedule`).
  Optional `verify_runs_on` affects only `Mercury verify` (default `ubuntu-latest`) and accepts a literal runner string or a non-empty list of literal labels. Do not edit them by hand; change the params and run the installer from a released Mercury commit.
- Scheduled updates use the integration branch's workflow. When the default branch differs, its scheduled job dispatches the workflow to the integration branch. The job gives a green update a chance to merge before publishing the latest released Mercury commit in the single `mercury/update-*` pull request.
- A successful check workflow on the update PR triggers a merge check for that exact commit. The trigger becomes active when the updated workflow reaches the default branch. The updater squash-merges only when the source commit is on Mercury's `master` and descends from the recorded one, only Mercury-managed paths changed, and the project's required checks plus the `Mercury verify` GitHub Actions check run are green on the current head. Paths the new release stops shipping may only be deleted. A scheduled run can check again if any condition is still pending.
- Do not push to, force-push or rebase a `mercury/update-*` branch, do not edit `.mercury/config.json` inside an update pull request, and do not merge an update pull request by hand to get around a failed condition; fix the cause or ask the project owner.
