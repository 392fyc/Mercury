# Why this dispatcher is narrow

The queue carries authenticated metadata, not trusted work instructions. A local installation registry is the authority that binds one event ID, task/request pair, kind, body hash, thread IDs, expiry, and direct human authorization record. The expiry is repeated in the authorization record, registry, and body; it must match exactly, remain in the future, and fall within 24 hours of the direct authorization timestamp. Queue data is compared with that registration before a native model turn can start.

The first dispatcher handles only `native-event-probe/1`. The probe demonstrates the complete local notification path without granting a general workflow runner, project access policy, callback interpreter, or shell command interface. Its only model output is a strict receipt. The controller verifies file bytes and receipt values, so a model cannot establish its own identity or hash.

At-most-once behavior favors a visible blocked record over an automatic retry. A durable `running` claim is written before spawn. If the process disappears, the next owner-controlled invocation blocks that claim rather than repeating a possibly completed model turn. After the controller verifies the output, it persists the receipt before network consumption. This permits safe consume recovery without repeating inference.

The local receipt state and gateway consumption state answer different questions. A verified receipt proves that the controller accepted one completed local turn. A gateway confirmation proves that the remote queue marked that same event consumed. Only the second result advances the independent local cursor. If an already confirmed local event is replayed with remote status `pending` or `sent`, the worker retries idempotent consume using the saved receipt. It advances directly only when the current remote event says `consumed`; a previous local confirmation cannot substitute for the current server state.

The JSONL parser uses a positive allowlist for event and item types. An unrecognized type blocks the turn before receipt acceptance, so newly introduced native operations do not silently pass through an old denylist.

The native CLI stays explicit: a fixed absolute `codex.exe`, one model and provider, ephemeral session, read-only sandbox, strict configuration, structured JSONL, and a controller-owned output schema. Before inference it disables the reviewed CLI feature set for shell, MCP/apps, browser, image, multi-agent, hooks, memories, sleep, artifact, goals, web search, and experimental user-input requests. It sets `project_root_markers=[]` to keep project discovery at the worker directory. This is a pinned configuration, not a claim that the model protocol exposes no tool declarations. The child retains the existing `CODEX_HOME` and authentication environment, removes the higher-priority `CODEX_EXEC_SERVER_NOISE_*` selectors without reading or logging their values, sets `CODEX_EXEC_SERVER_URL=none`, and refuses custom execution environments. The parent environment remains unchanged. It also refuses system-managed Codex files and project configuration in the worker path by checking existence without reading file contents. The one exact user config under `CODEX_HOME` is ignored by the CLI and exempted from the ancestor scan. The reviewed installation baseline is Windows CLI `0.156.1`; other platforms, account eligibility, or managed configuration sources require a separate review. A synthetic probe is a local worker execution; it is not a continuation of the desktop chat.
