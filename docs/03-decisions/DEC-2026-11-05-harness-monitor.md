# Harness 报告是 M1 的具名例外

Date: 2026-11-05

## 决定

用户决定把 `tools/harness_monitor/` 放进 Mercury，并给予特许：它是检验 harness 自身是否成立的工具。Issue：[#755](https://github.com/392fyc/Mercury/issues/755)。

M1 规定 Mercury 不自建编排层、CLI 包装或桌面应用。这个工具是唯一的例外，理由是 Mercury 需要知道自己配置的入口有没有被 Agent 用上，否则无法判断哪里该改。

## 例外的边界

- **目的只有一个**：分析本机 harness 层，把结果反馈给项目改进。不做通用的 Agent 监控产品。
- **尽量轻量**：运行一次、生成一份静态报告，不常驻，不开端口，不做告警。定期运行交给系统计划任务。
- **不下发**：它在 `tools/` 下，不是 pack，不安装到下游项目。
- **不存内容**：只保存计数和工具、skill、项目的名称，会话只留哈希。私人项目的排除名单只放在本机被忽略的配置里。
- **规则与验证绑定**：`rules.py` 的哈希和统计范围内的工具清单记录在 `validation.json`，测试机械校验；改动任何一个都必须重新验证。

超出这些边界的改动需要新的决定。

## 与其他原则的关系

- **P1**：日志采集用 agentsview，不自研；它的文档里没有自定义调用分类的入口，所以分类和验证状态这部分自写。
- **P2**：`tools/` 是内部工具，不受 200 行限制。分类规则是业务逻辑，也不属于 `packs/<pack>/build/` 转换层。真正接触 agentsview 的代码（字段校验、环境变量和同步）约 40 行，本身也在 200 行以内。
- **P3**：没有其他代码依赖它，拆除清单见工具的 README。
- **P4**：它测量实际行为，模型变强后依然成立。规则需要随工具变化重新验证，这是已知的维护成本。
- **E1**：agentsview 是用户在本机安装的程序，不是仓库挂载的依赖，不走 submodule。仓库不拉取也不复制它的代码。这是 E1 之外的另一种用法，写在 M4 里：版本钉在代码里并在运行时校验，许可证和安装包哈希记在工具的 README。

## 代价

- 本机多一份约 1.4 GB 的完整对话副本，必须留在本机。
- 规则只验证了现有日志，需要隔一段时间重新抽检；14 格里有 5 格仍是“未验证”。
- 报告只能说明查没查，不能说明查到的内容有没有被用上。
