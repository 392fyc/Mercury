# Harness 报告的分类规则验证（2026-11）

Issue：[#755](https://github.com/392fyc/Mercury/issues/755)、[#758](https://github.com/392fyc/Mercury/issues/758)、[#760](https://github.com/392fyc/Mercury/issues/760)。这里记录 `tools/harness_monitor/rules.py` 为什么可信、可信到什么程度。原始样本含对话内容，只留在本机，不进仓库。

## 要回答的问题

分类规则把一次工具调用判成“读了记忆”“查了网络”等类别。我们要知道两件事：

- **精确率**：规则说是这一类的调用里，有多少真的是。
- **召回率**：真正属于这一类的调用里，规则找到了多少。

宿主（Claude、Codex）和 8 个类别组成 16 格，每格单独判断。本机关闭了 Claude 自动记忆，日志里没有这类调用，那一格不适用，实际 15 格。一旦开启，`.claude/projects/*/memory` 会被算成项目记忆，要重新拆分。

第五版（#758）把“记忆读取”拆成项目记忆和宿主自带记忆，并把记忆目录下 `evidence` 里的文件排除在外。全量回归 38,629 条调用：Claude 没有任何标签变化，Codex 的跨 lane 消息、skill 文档、知识库、规则文件、网络查询和 GitHub 六类也没有变化。所以这些格子沿用第四版的结论，只有 Claude 项目记忆、Codex 项目记忆、Codex 宿主自带记忆三格重新验证。

第六到第八版（#760）只处理 Codex 的项目记忆和网络查询两格。一条 Codex 调用常是一段 JS 脚本，里面打包多个操作，命令可能包在 `bash(...)` 字符串里。规则改动大多在两个宿主共用的函数里，只有二次解包限于 Codex 的 `exec` 和 `js`。全量回归 39,337 条调用：相对第五版，Codex 项目记忆 405 变 387，Codex 网络查询 993 变 1071，Claude 网络查询 681 变 682，其余格子没有任何变化。Claude 多的 1 条是脚本里 `.goto` 打开 `trial.local`，很可能是误判，没有核实这个主机。所以 Claude 各格沿用结论的依据是“这批日志上没有变化”，不是“代码没有碰到”：用构造的命令可以让 Claude 的项目记忆变化，比如 `.sot/memory/x/lanes/ui/inbox.md` 不再算记忆。

## 方法

1. 规则先冻结并记录哈希，方案先写好，再抽样。抽样种子固定。
2. 第四版只用规则没见过的调用，共 901 条；第五版重抽 627 条，其中点名记忆路径而未算读取的 Claude 调用全取。都排除私人项目。第六到第八版共再抽 1,790 条，每轮只用之前没抽过的行，发给 OpenAI 前整行剔除疑似含密钥的调用。
3. Sonnet 和 Opus 互不知情地标注全部样本，两者一致即为标准答案。第四版 883 条一致，其余 18 条交第三个模型 Fable（同样是 Claude 系列）裁定取多数，2 条没有多数，从分母剔除。第五版 618 条一致，其余 9 条同样裁定，全部有多数。第六到第八版改由 Sonnet 和 OpenAI `gpt-6.1-sol` 互不知情地标注，分歧交 Opus 裁定，1,790 条里有 16 条分歧，全部有多数。主会话不参与裁定。
4. 过线标准：精确率的 95% Wilson 下限不低于 80%，且召回率的“关键词下限”不低于 70%。

关键词下限假设“完全不含相关关键词的调用几乎不属于这一类”。不用这个假设的严格下限所有格子都低于 70%，要压到 70% 以上，每个宿主需要几百到上千条随机样本。

## 结果

每格写的是：精确率 / 估计召回率（关键词下限）。

| 类别 | Claude | Codex |
|---|---|---|
| 项目记忆（Claude 第五版，Codex 第八版） | 40/40 / 92%（70%）可用 | 93/100 / 95%（83%）可用 |
| 宿主自带记忆（第五版） | 不适用 | 40/40 / 96%（81%）可用 |
| 跨 lane 消息 | 37/40 / 100%（68%）未验证 | 40/40 / 83%（76%）可用 |
| skill 文档 | 33/39 / 89%（46%）未验证 | 39/40 / 100%（77%）可用 |
| 知识库 | 38/40 / 93%（82%）可用 | 39/40 / 88%（77%）可用 |
| 规则文件 | 36/39 / 96%（84%）未验证 | 39/40 / 94%（84%）可用 |
| 网络查询（Codex 第六版） | 40/40 / 100%（93%）可用 | 40/40 / 94%（77%）可用 |
| GitHub | 40/40 / 99%（97%）可用 | 40/40 / 94%（84%）可用 |

12 格可用，3 格未验证：

- **Claude 跨 lane 消息**：定向样本里没有漏判，但这类调用少、候选多，样本量压不低上限。
- **Claude skill 文档**：只算哈希、查 BOM、看 git 日志或写入 `SKILL.md` 被算成读取。
- **Claude 规则文件**：脚本里只把 `AGENTS.md` 当字符串，被算成读取。

Codex 项目记忆走了三版才过线，过程要如实看：

| 版本 | 精确率（95% 下限） | 估计召回率 | 关键词下限 | 结果 |
|---|---|---|---|---|
| 第六版，第一轮 | 38/40（83.5%） | 94% | 65.8% | 未过 |
| 第六版，补抽 350 条 | 沿用 | 79% | 67.0% | 未过，真实漏判比第一轮多 |
| 第七版 | 33/40（68.0%） | 97% | 84.5% | 未过，解包时把自带记忆的提示文字算成了项目记忆 |
| 第八版 | 93/100（86.3%） | 95% | 82.6% | 过线 |

第六版第一轮的 94% 是抽样偏乐观，补抽后才看到真实漏判。每一轮都在抽样前写定方案，轮内看到结果后没有改规则或门槛。但第六版补抽和第七版的方案都写了“这次就是最终结论”，失败后仍开了新一版：补抽、第七版和第八版都由用户逐次决定继续。所以“可用”依赖这几次决定，读者应把它看成比一次过线更弱的证据。第八版在已标注的 1,240 行上还有 4 条误判和 8 条漏判没有处理；把这 8 条全算进漏判，关键词下限约 81%，仍过线。

## 局限

- 第五版及之前的三位审查者都是 Claude 系列模型。只有 Codex 项目记忆和网络查询两格有跨厂商标注，Claude 各格没有。
- 审查者只看调用内容，看不到执行结果和之前的工作目录。
- 第五版抽样时，第四版用过的样本已无法排除，两轮可能有重合；所有行都重新标注，不复用旧结论。设计第五版时主会话看过部分日志。
- Claude 项目记忆的“可用”差一票就翻转：189 条候选里 8 条真漏算时下限 70.3%，9 条时 69.8%。这 8 条里有 5 条靠第三方裁定，另有 2 条被裁定为非漏算。
- 这 8 条漏算的原因不止一种：引号里的分号把命令切开（`sed -n '1,41p;198,400p'`），读取和写入出现在同一条命令时整条算成写入，短脚本里的路径字面量被过滤。没有一条是变量丢失造成的。修这些要改命令切分或脚本判断，会影响其他类别，没有做。
- 规则按路径逐个判断，有几种写法会判错，日志里没有造成实际丢失：路径含空格（`.codex/projects/my proj/memory`）、逗号相连的多个路径、项目路径本身含 `evidence` 目录。
- `LANES.md` 和 `LANE.md` 按记忆算，它们是 lane 登记文件，不全是回忆内容。
- 同一条调用里只要写了记忆，读取就不计。这沿用了第四版，会抹掉“读宿主记忆、同时写项目检查点”这种调用：Codex 320 条写入调用里有 27 条点名了宿主记忆，是这一格漏算的上限。第八版的例外是 14 条 Codex 调用：第一遍把打印或箭头函数当成写入，二次解包后算读取。
- `.codex/projects/*/memory` 按宿主自带记忆算，这个归属没有官方依据，标注标准也写了同样的定义，所以盲审验证不了它。日志里只有 6 条，都在用户主目录下，目前这个目录下没有 `memory` 子目录。
- Codex 项目记忆试了三版才过线，门槛没变，但多次尝试本身会抬高碰巧过线的机会。规则是看着前几轮已标注的行设计的；这些行没有进入第八版的样本，但针对的写法来自同一批日志。
- 回读校验和真正查阅的边界本来就模糊。第八版把“算哈希并和预期值比较”的回读都算作不读取，除非同一调用里有直接点名记忆库的 `Get-Content`、`cat`、`sed`、`rg`、`head` 或 `tail`。这条判断看整段调用，不看是否针对同一文件，所以 `Select-String`、`awk`、`-Action Read` 旁边有无关的哈希比较时也会漏算。日志里这条规则共去掉 21 条，其中带这三种写法的 0 条。同样写法的调用，标注者给过不同结果。
- 第八版抽到 7 条误判，确认原因的有两种：`$lane` 变量拼出的 `evidence` 路径，以及只列 `.sot/memory/projects` 目录的调用。漏判有 `cat "$p"` 这种路径来自命令输出的写法。
- Codex 网络查询认不出 `git ls-remote`、`HttpClient`、`uv pip install --index-url` 和脚本自定义的 `fetch`，抽到的 8 条漏判都属于这类。构造的命令也能造成误判：`--client=curl` 后面带地址，或 `echo` 输出一段含 `.goto('https://...')` 的文字。日志里 `=` 形式新增 9 条、浏览器形式新增 69 条，没有逐条复核；精确率 40/40 是同一批规则抽的。
- 第六、七版抽样时，路径层的正则少了反斜杠，Windows 写法的记忆路径落到了关键词层。两层合起来覆盖范围不变，召回估计仍然成立；第八版已修正。
- 一条 Codex 调用常打包多个操作，所以调用数不能和 Claude 直接比，会话数可以。
- 二次解包只服务于项目记忆，所以被包在 `bash(...)` 里的 skill 文档、知识库等读取仍可能漏算。这些格子的验证结论来自未解包的规则。
- `lane-bus wait` 不算消息读取。`Agent`、`SendMessage` 和 Claude 浏览器工具不在范围内。
- 结论只代表验证时的日志。工具和模型习惯变了要重新抽检。

## 工具的实现核对

2026-11-05 在真实日志上运行 `monitor.py`：首次 31 秒，增量约 1 秒，结束后没有残留进程。用独立代码按验证时的过滤条件重算，两个宿主 7 个类别和总数共 16 个数字全部一致。
