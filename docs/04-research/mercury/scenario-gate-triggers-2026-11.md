# 交付检查该由什么触发（2026-11）

Issue：[#779](https://github.com/392fyc/Mercury/issues/779)。现行做法见 [scenario-gate.md](../../02-guides/scenario-gate.md)。

## 结论

- **按回复内容自动判断“这是不是研究交付”不成立。** 从提示判断最多抓到三成；让小模型看最终回复能抓到 21/22，但会把七成回复都判成交付。
- **两个被广泛采用的开源项目都把强制放在工具调用上，不检查聊天里的结论。** 它们不能原样用来检查交付，但说明了强制该放在哪里。
- **采用的做法：** 改文件这个动作本身触发“必读规则已读”的检查；研究和设计用用户实际使用的短语触发，命中即准但覆盖面小，其余靠 lane 和前缀。
- **数字都来自一个用户的两三个项目，样本小，只说明方向。**

## 术语

- **交付：** 回复给出调查或评估的结论，或带选定数值的方案，供用户决策或依赖。进度汇报、实现和合并报告不算。
- **盲评：** 由一个只读角色标注，它看不到别人的标注，也看不到模型的判断。
- **提示：** 用户输入的一条消息。**回合：** 一条提示加上随后的全部动作。

## 公开做法里的五类触发

| 类型 | 例子 | 是否检查聊天里的结论 |
|---|---|---|
| 用户输入前缀或命令 | Claude Code 的 `/goal` | 取决于用户记得用 |
| 出口处的可观察状态 | [claude-verify-before-stop](https://github.com/ianymu/claude-verify-before-stop)：有文件改动就要求核查记录 | 否，看的是文件改动 |
| 动作点常开，可关 | [tdd-guard](https://github.com/nizos/tdd-guard) 及其后继 [probity](https://github.com/nizos/probity)：每次写文件和每条命令之前按规则检查 | 否，规则只接受“写文件”和“命令”两种动作 |
| 对提示分类 | [claude-code-infrastructure-showcase](https://github.com/diet103/claude-code-infrastructure-showcase)：按关键词和意图正则建议技能，可选用模型分类 | 否，拦截部分在改文件之前 |
| 出口处由另一个模型判断 | Claude Code 原生的提示型钩子 | 是，但官方说明它不是确定性的；Codex 会跳过这种钩子 |

另有一份用户报告（[anthropics/claude-code#99216](https://github.com/anthropics/claude-code/issues/99216)）：规则文件、记忆、每条消息的注入和工具拦截都在，一个会话里仍有 7 次未核实的断言，全部由外部检查发现。

## 实验一：五种触发方式

题目是历史回合的最终回复，问题是“这条回复是不是交付”。

**第一批，30 条，偏向联网多的回合**（联网 3 次以上的 14 条全取，另随机 16 条）。标注由主代理在运行任何判断之前写下，18 条是交付：

| 触发方式 | 抓到 | 误报 |
|---|---|---|
| 提示以“研究：”开头 | 0/18 | 0/12 |
| 关键词加意图正则 | 8/18 | 2/12 |
| 小模型只看提示 | 13/18 | 1/12 |
| 回合里联网 3 次以上 | 11/18 | 3/12 |
| 小模型看最终回复 | 18/18 | 7/12 |
| 小模型看提示，或联网 3 次以上 | 17/18 | 3/12 |

**第二批，60 条，纯随机**，由只读角色盲评，22 条是交付，33 条不是，5 条拿不准（不计）：

| 触发方式 | 抓到 | 误报 |
|---|---|---|
| 提示以“研究：”开头 | 0/22 | 0/33 |
| 回合里联网 3 次以上 | 0/22 | 0/33 |
| 关键词加意图正则 | 7/22 | 5/33 |
| 小模型只看提示 | 7/22 | 3/33 |
| 小模型看提示，或联网 3 次以上 | 7/22 | 3/33 |
| 小模型看最终回复 | 21/22 | 16/33 |

第一批里最好的组合到第二批只抓到三成。原因有两个：组合是看过第一批之后才挑的；第一批里联网多的回合占 47%，而它们在全部回合里只占约 3%。

被漏掉的交付，提示多是“可以运行”“再重新做一批”“现在整理”这类延续上文的短句。回复会不会成为交付，从提示里看不出来。小模型看最终回复时，60 条里判了 42 条是交付，给出的理由多是“回复里列了需要用户决定的事项”。

盲评里交付占三分之一以上。如果每条都要补小节并跑一次独立核查，负担会很重，这是放弃“自动判断每条回复”的另一个原因。

## 实验二：从用户的用词里取触发短语

数据是用户在三个项目里亲手输入的 868 条提示（Claude Code 和 Codex 的主会话；去掉了粘贴内容、延续摘要、代理写的消息和工具生成的内容）。中位长度 27 字。

- 单个词不按任务类型分家。例如这 868 条里有 20 条提示含“方案”，其中 80% 的回合是在改文件。所以规则用的是下达任务时的短语。
- 收紧后的两组短语各命中 19 条。把这 37 条和 60 条随机未命中的提示混排后盲评：研究类 19 条里 18 条确是在要求查证，设计类 19 条里 17 条确是在要求出设计。
- 60 条未命中里仍有 9 条查证请求、6 条设计请求。按比例推算，短语只覆盖一成多的实际请求。
- 设计 lane 的会话有 131 条提示，设计短语只命中其中 6 条。所以设计场景的主要信号是 lane，不是短语。

短语是读了全部命中结果之后才收紧的，准确率是在同一批数据上算的，换一批会话可能更低。

## 工程上核实过的事

- 用订阅调用小模型一次：Claude Code 约 5 秒（其中模型约 1 秒），Codex 约 11 秒。Claude Code 的 `--bare` 精简模式只认 API key，不能用订阅。
- Codex 只运行命令型和 MCP 工具型钩子；它的内置联网搜索不经过钩子。
- 在真实会话里验证过：研究检查的启用、打回、核查记录和通过（Claude Code 和 Codex）；改文件前的拦截、读文件记录和放行（Claude Code）。

## 未核实

- 两批样本的标注都只有一个标注者。
- 小模型的判断只试了一种说法；更窄的说法可能降低误报。
- 改文件前的拦截在 Codex 上还没有实测；Codex 的 shell 读取识别是近似的。
- 短语的准确率没有在新的会话上复验。

## 之后看什么

跑一段时间后回看：每次触发时显示给用户的那一行里，误触发有多少；漏掉的请求都是什么样的句子。再决定要不要增减短语，或做一个辅助写提示的小工具。
