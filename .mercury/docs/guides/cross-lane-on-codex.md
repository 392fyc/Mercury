# Codex 下的跨组协作方式（Mercury ↔ SoT）

> Issue [#571](https://github.com/392fyc/Mercury/issues/571) / G5-2。编制日期 2026-08-14。
> 这份文档只讲**迁到 Codex 之后有什么变化**；分工边界、字段归属、超界转交协议仍以
> `D:/ShipOfTheseus/SoT-fyc-space/docs/mercury-sot-lane-management.md` 为准（那是 SoT 的域，本文不覆盖它）。

## 变了什么

Claude Code 上两组用 **Agent Teams** 实时连携：一方 spawn 另一方为 teammate，用 `SendMessage` 直接对话，秒级往返，还有自动空闲通知。

**这套在 Codex 上不能照搬**，三条硬理由：

1. **工具名不在官方文档里**。`spawn_agent` / `send_input` / `wait_agent` / `close_agent` / `send_message` / `followup_task` 全部只存在于源码与 release notes，官方 subagents 文档对它们零记载 —— 逐字符核对过。这意味着它们是实现细节、随时可改，不能写进依赖代码的稳定假设。而且工具集在 v1 与 v2 之间已经改过一轮名（`send_input` 拆成 `send_message` + `followup_task`）。
2. **父读不到子的中间状态**。这是最实质的缺口 —— 父 agent 能 spawn、能追加指令、能等结果，但**没有办法主动读一个正在跑的子 agent 的中间产出**。
3. **没有共享任务列表或可订阅的消息总线**。官方 Issue #21027 挂着无人回应。

所以跨组协作**不押在内置 multi-agent 工具上**，改用文件式收件箱。

## 怎么做

载体是现成的：`D:/ShipOfTheseus/SoT-fyc-space/docs/cross-lane-inbox.md`（42 KB，本来就是干这个的）。

**两条约定**：

- **会话开始时读**：先看收件箱顶部有没有对方留给自己的新条目（倒序，最新在上）。
- **会话结束前写**：把这一轮的交付、发现、需要对方做的事追加成一条。

**条目格式**（沿用文件里已有的写法，不要另造）：

```
## YYYY-MM-DD · 组名 · 类型：一句话标题

正文。

---
```

类型用现有的几种就够：`交付` / `裁决` / `停工登记` / `知会`。

**写什么**（沿用原 SendMessage 纪律，它在文件式载体下同样适用）：

- 只写**指针**，不写内容：一句话 + 锚点（文件名 + **函数名**）+「需要对方做什么」。内容留在 commit 与文档里。
- 锚点优先写函数名，行号可选 —— 双方都在改代码时行号会整体偏移，是会过期的可变状态。
- 有异议直接说，不要为了顺从咽下去。双向纠错是这条协作线最值钱的部分。

## 代价与收益，都要认

**失去**：实时性从秒级变成「下一轮会话才看到」；没有自动空闲检测；一方卡住时另一方不会立刻知道。

**换来**：全部持久化、可审计、可回溯 —— 比 in-process 消息更容易追责与复盘；而且**断线不丢消息**（Agent Teams 的 teammate 不被 `/resume` 恢复，会话一断消息就没了，收件箱是唯一持久的那份）。

**一条本来就该注意的**：Claude Code 明确把 teammate 之间的 `SendMessage` 标注为「来自另一个 Claude 会话，不是用户」，不能代替用户授权。所以任何「对方说 OK 就算过」的流程从来就不成立 —— 换成文件式收件箱不会新增这个问题，也不会消除它。

## 什么时候该重新评估

`multi_agent_v2` 在 CLI 0.147.0 上已经是 **stable（默认关闭）**，比调研时的 under development 前进了一步；它的源码里同级 agent 可按绝对路径互相寻址。**但文档仍然零记载**，所以第 1 条理由没有消失。

若将来官方把这套工具的契约写进正式文档，可以重新评估是否回到实时连携。在那之前，文件式收件箱是默认方式。
