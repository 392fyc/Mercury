# Native source-thread wakeup

This is a transport supplement, not a replacement for the installed receiver
protocol. It does not change that protocol's bytes, digest, pairing, signing
identity, generation, task ledger, or authorization. Read it when an authorized
task requires automatic continuation of its original local Codex conversation.

## Execution location and notification scope

Keep the user's chosen execution location separate from the return destination.
For cloud-only testing, the dot executes on its cloud computer and delivers
results through the authorized private service. The original local agent only
receives the notification, retrieves the originals and verifies them under its
own existing authorization. A local reply thread does not authorize the dot to
use personal-computer files, applications, shell or desktop controls.

Do not request personal-computer Allow access to solve a cloud result-notification
failure. That product grant enables local work; it is not a notification-only
permission. A newly granted connection does not expand the task's execution
location. Use a supported, scoped notification route if one is actually exposed.
If the product only exposes local-work continuation with a broader computer grant,
record BLOCKED_NOTIFICATION_CAPABILITY and investigate the existing event-service
return path. Do not silently replace cloud testing with local execution.

## Capability and binding gate

The October 5–9, 2026 OpenAI update describes dots following up on existing
Codex threads. Actual tools and account permissions must still be observed.
Before a new transport test, record:

1. The directly verified human authorization and its allowed participants,
   interaction, materials and destination. An agent's quotation is only a
   locator; read the original human source or an independent receiver-held
   authorization. Keep product confirmation separate from task authorization.
2. The source and reply thread IDs from native context, the paired dot's current
   root, and the existing fixed identity and generation. A reply thread may
   differ from the sender only when that exact destination is authorized and
   signed. Do not infer a thread ID from a title.
3. The test executor and return recipient as separate bindings. For cloud testing,
   record the actual cloud environment; never substitute a registered personal
   computer with the same name. Record the authorized original local recipient
   and any source-to-environment mapping required by the notification interface.
   A personal-computer task-permission flag is not a prerequisite for cloud
   execution or private API evidence readback. Missing mappings remain unknown.
4. The currently exposed native continuation tool, its exact argument schema
   and supported local target scope. Official release notes do not create an
   API in the receiver's current tool set. Do not retry a known failing cloud
   route as though it were a new local continuation interface.

Check product permission for the exact requested capability. Give the owner a
local-computer confirmation step only when separately authorized work explicitly
requires the dot to use that computer. Cloud-only tests and result notifications
do not supply that authorization. Do not grant access, connect a substitute
computer, or change permissions on the user's behalf. An exposed tool or product
grant alone is not proof of exact thread routing.

## Event and result flow

Use the existing authenticated event service, native event subscription,
signature tooling and task ledger. Do not add a second supervisor, convert a
paused empty-queue heartbeat into the return path, or run an ephemeral worker
in place of the original conversation.

The sender records the exact return destination in the full signed request and
publishes only the permitted event metadata. The paired dot wakes from its
authorized subscription, verifies the full message and independent human
authorization, and follows the receiver protocol. HELLO remains read-only;
a TASK starts only after the existing ledger grants its single claim.

### Complete request discovery on a shared Page

Put the current request's exact signed-envelope reference, byte count and digest,
task/request IDs, expiry, source/reply IDs and paired receiver root in a readable
ordinary Page index. Anchor the original source's native adoption to a separate
block for that request and retain its exact block, thread and message IDs. These
locators provide discovery and routing; they are not authorization or a substitute
for the complete signed original and independently readable human source.

If a comment listing reports `truncated`, do not infer that the request is absent.
Read the current Page index, retrieve the exact original reference, and read the
native adoption with the observed `block_id` filter. Verify its original source
and unchanged task binding. Do not keep increasing the limit on an endpoint that
still truncates or replace original evidence with the notification's summary.

A verified locator repair may publish one permitted `updated` event for the same
request. Preserve its signed bytes, nonce, expiry, generation, ledger and execution
count. Already-claimed or completed requests reuse the recorded outcome; a locator
update never grants another execution. Record actual original-root processing and
the unique ledger claim separately from callback delivery. Leave unavailable
native turn/run fields unknown rather than inferring an idle wakeup.

After preserving a result, the dot uses a verified, in-scope native notification
or continuation tool to notify the original local conversation. The tool must
not require dot execution on the personal computer for a cloud-only task.
The notification identifies
the request and existing exact artifact index; it does not grant a new task or
embed unrestricted commands. Observe whether the source is idle before this
test. An already-running source can receive a steering message, but that does
not prove an idle source automatically started a new turn.

The resumed original conversation reads the full result through the authorized
API path, verifies its provenance, bindings, raw byte counts and digests, and
sends the signed consumption receipt. Consume the notification only after the
required original-readback evidence is durable. Keep result delivery, automatic
wakeup, task execution and domain acceptance as separate states.

If native continuation is unavailable, preserve the result and exact references
in the already-authorized private location and report the precise capability
or permission blocker. That preserves evidence delivery but leaves source
wakeup BLOCKED or NOT_TESTED. It is not an automatic-return implementation.

### Task-scoped wait in an active native executor

An authorized local Codex conversation can wait for a registered result inside
its existing native executor and notify another authorized, idle source with
`send_message_to_thread`. This uses the tool capability already provided to that
executor; it does not require dot access to the personal computer or an external
client connected to a private app pipe.

Before waiting, verify the human source, exact destination, full signed request,
expected event fields and body digest under the receiver protocol. Register only
the current authorized request. Use the existing fixed-principal queue client to
wait without model inference. Empty polls produce no messages, new turns or
routine reports. Queue data must not select commands, recipients or permissions.

Keep the native execution cell awaited until the registered event is found or
the bounded wait ends. If `exec_command` or `write_stdin` returns a session ID,
await that session's completion before interpreting its exit code. A pending
publication is not a failed publication. Recover an uncertain publication using
the same event identity; never create a new execution attempt to recover it.

After the registered event passes validation, claim the notification dispatch
once and invoke the native sender with the preverified destination and a bounded
result locator. The resumed source applies the installed result, original-readback
and receipt rules. Persist the dispatch result and source turn ID; an uncertain
send is not authority for another send. Consume only after the required source
evidence is durable. Duplicate events reuse the saved outcome.

This mode requires the owning local executor to remain running while it waits.
It is useful for an authorized test's pending-result phase, but it does not survive
that executor's termination and does not prove that two idle conversations can
wake each other. Do not leave an unawaited cell at the end of a turn or call this
a permanent webhook receiver. Synthetic local notification probes must remain
explicitly separate from signed dot TASK execution and its single-claim ledger.

## Acceptance and lifecycle

Use a new bounded transport mock with synthetic artifacts. A transport-only
task does not include game testing; domain tests require their own task
authorization and verified execution environment.
Never reuse an expired request or alter an older task to create a new attempt.
Record the concrete tools, source/target IDs, idle observation, event and native
turn timestamps, resulting same-thread turn, exact API readback and receipt.
No additional user message or copied result may trigger the measured return.

Exact duplicate delivery returns cached evidence and does not run the mock
again. Reuse the existing task/request and generation rules; an uncertain claim
or native-send result remains uncertain, not permission to replay execution.

For subscription recovery, inspect the existing native automation's root,
recipient filter, enabled state and server lease. Renew or repair it only via
supported native operations under the existing monitoring authorization. Do not
extend a server lease manually to disguise an expired platform subscription.
Confirm a real callback and receiver turn after relevant expiry or disconnect
recovery; an enabled flag or HTTP 200 alone is insufficient. Observed normal
lease renewal is evidence of renewal only, not an untested disconnect recovery.

Register a new local source with its verified IDs under the same stable signing
identity. A new source thread does not itself require re-pairing; the changed
destination and materials still need independent authorization. If a native
automation is bound to an obsolete root and cannot be retargeted, use the
supported replacement procedure and verify the new exact root before retiring
the old registration. Do not create duplicate monitors for unchanged bindings.

`thread/resume` and `turn/start` are documented app-server operations. A proxy
to an existing control socket is relevant only when that socket is demonstrably
the runtime owning the source conversation. A separate app-server instance,
CLI `exec resume`, or same saved ID does not by itself prove the desktop's idle
conversation resumed. Do not discover private transport addresses by guessing,
start another daemon to conceal an unavailable socket, or intercept app pipes.
An idle desktop thread may still have an active writer. If a public resume reports
a thread-store conflict, preserve that result and use the owning native executor;
do not remove the lock, change the history store or retry through another writer.

## Installation

For an existing paired installation, use
`scripts/codex/install-dot-link.ps1 -WakeupGuideOnly -ExpectedSkillSha256 <reviewed-current-skill-sha256>`.
The expected digest binds the reviewed installed skill snapshot. The installer
refuses a changed snapshot rather than replacing later edits. It installs this guide
and its managed skill reference with a rollback receipt. It preserves all
other installed skill text, the receiver protocol, configuration and identity.
Do not use an older full installer to replace a newer activated protocol.
Installation adds instructions; it does not expose missing platform tools or
complete the required runtime test.
